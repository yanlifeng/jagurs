## 2. 现在怎样分开

| 职责 | 本轮代码位置 | 放什么、不放什么 |

| 耦合输出接口 | 新增 `src/mod_coupling_output.f90` | 管理额外输出时刻及原生四场的输出入口，不做重新插值或物理量转换 |

### 本轮真正改动的求解器位置

- `JAGURS.f90`：加入一次配置初始化；原来额外帧判断改为接口调用；四个原生场输出调用移入新模块。原来计算数组、写出顺序、文件名、数组范围及输出精度不变。
- `mod_coupling_output.f90`：新增输出接口。rank 0 读取配置再广播；配置非法直接报错，避免各进程采用不同策略。
- `mod_onefile.f90`：与上一轮 `opt01/overlay` 的文件完全相同，SHA256 为 `3c2b77aaf620f8be76980f40670b6bf3b658d3e2c2dabc96e18d8cbef16da137`。默认关闭集合汇集开关；灵晟构建显式打开。仍禁止把此 CPU 优化与 `USE_GPU` 同时启用。
- 现有 Makefile：只在主程序之前加入新模块的编译/链接顺序，不改变各平台原有编译选项。并未实际验证所有历史编译器和 GPU Makefile。

原有震源文件读取、整数时间索引修复和施源顺序保持原位、保持原样；这部分与时间推进紧密关联，**没有在本轮顺手改写**。本轮也不新增地震转换器、sECOM 算法或在线内存耦合。

## 3. 耦合数据约定必须继续守住

输出接口保留的是**原生字段**，不是已经处理好的漫滩边界：

| 字段 | 物理含义与约定 |
|---|---|
| `eta_raw` | 相对于案例背景面的水位扰动，单位 m；本 Hirota 案例背景面为 −0.42 m T.P. |
| `qx_raw` | 向东的单位宽度流量，单位 m²/s，不是 m/s 的流速 |
| `qy_south_raw` | 向南的单位宽度流量，单位 m²/s；转成向北方向时必须变号 |
| `depth_raw` | 当前背景水深字段 H，向下为正；瞬时总水深 D=H+η，不能直接把 H 当 D |

保留网格交错位置和时间交错：本案例 SD03 的通量相对标注水位时刻约早半步（0.05 s）。不能仅凭四个文件名的时间标签相同就当作同一时刻、同一空间位置。计算保持 FP64；当前 GRD 场值保存为 FP32。坐标、方向、高程基准、时间层和精度都应写入后续接口说明，不能让后端自行猜测。

配置 `extra_output_steps` 指**全局 dt 对应的步号**，不是各嵌套层的局部步号；原有 `plotgrd`、`velgrd=2` 等限制仍生效。已有案例无需新增配置即可复现；新案例应显式设置自己的步号，或 `extra_output_count=0` 关闭额外帧。

## 5. 后续优化次序

1. **先做共用优化。** 继续看实测剖析：减少重复遍历/临时数组，优化输出汇集、嵌套交换和通信等待。每次只改变一种机制，保留可切回原实现的开关，用同一案例和输出量对照。当前 root 集中输出仍是瓶颈候选；集合汇集也会占用 root 额外内存，大网格要评估分块汇集或并行 I/O。
2. **再做灵晟特化。** 编译器向量化/SVE、NUMA 首次触碰、HBM 放置、绑核和 MPI/OpenMP 比例放到平台配方或明确的后端实现，不把机器编号、HBM 路径写进通用方程。保留原 `-ffp-contract=off`；本阶段不靠 fast-math、混合精度或减少输出提速。
3. **单独排查高进程数偏差。** 历史 192 MPI、16×12 分解曾未通过严格通量回归，本次轻量整理不宣称修复。先定位边界/分区问题，再扩展有效并行规模，不能放宽阈值掩盖差异。
4. **然后接一个真实加速后端。** 优先挑水位更新或动量更新中的完整循环区域，保持数组尽量驻留设备并明确 halo 同步。不是把每个 `pow/sqrt` 包成一次设备调用，也不先把整个 Fortran 程序翻译成另一种语言。

## 6. 怎样为其他课题的统一编程框架留接口

现在先准备“可复现参考实现 + 明确的数据与执行约定”，不预设对方尚未定稿的 API。按照申报书中统一编程/算子库/运行时的分工，建议未来共同确定：

- **算子边界**：例如“一次水位更新”或“一次动量更新”；列清读入/写出数组、区域范围、halo 宽度、标量参数、依赖次序，允许框架做循环融合。
- **数据描述**：数据类型、尺寸、步长/布局、交错位置、单位、时间层、主机/设备位置，以及谁拥有、释放缓冲区。不要把复杂 Fortran 派生类型直接作为跨语言 ABI；若框架走 C/C++，可在边界增加小型 `ISO_C_BINDING` 包装，原 Fortran 参考实现仍保留。
- **执行与通信约定**：谁完成异步任务、何时保证边界数据就绪；CPU MPI、设备直传或经主机暂存由后端选择。必须先确认目标设备及通信栈能力，不能假设昇腾、CUDA GPU、曙光 DCU 的编程和 FP64 能力相同。
- **交付给框架团队的验收包**：同一输入、原 Fortran 参考结果、数值容差、完整案例、解析检查、算子剖析和通信量。框架接入后复用现有检查，不再创造另一套宽松真值。

本轮尚未实现通用设备内存管理、统一运行时 API 或 GPU 多节点后端。这些在接口与目标硬件确认后逐块接入，避免维护若干长期分叉的完整 JAGURS。
